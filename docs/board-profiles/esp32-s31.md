# ESP32-S31 firmware profile

**Date:** 2026-10-19. Status: bring-up profile — **partial**: the
chip facts below are sourced from Espressif's own announcement,
but Espressif has not published the S31 flash geometry, so the
flash map, security partitioning, and `efw_image` slot layout are
explicit stubs (see the sourcing rule in this directory's README).
Nothing in this profile invents a number the vendor has not
published.

The ESP32-S31 is Espressif's first dual-core RISC-V part with a
Gigabit Ethernet MAC and a full modern radio set (Wi-Fi 6,
Bluetooth 5.4, 802.15.4) on one die — the natural eFirmware target
for the org's wired+wireless gateway class of devices, and the
first ESP32 the org tracks from silicon launch (mass production
2026-07-27) rather than catching up to. This profile records what
is known, what eFirmware proposes to do with it, and exactly which
vendor data the remaining sections wait on.

## Board and chip (sourced)

- MCU: **Espressif ESP32-S31** — dual-core RISC-V @ 320 MHz (one
  core with 128-bit SIMD), plus a 40 MHz low-power core.
- Memory: **512 KB SRAM + 32 KB LP SRAM**. Flash size is **not
  published** in the announcement — see the flash-map stub below.
- Radios: **Wi-Fi 6**, **Bluetooth 5.4** (Classic + LE),
  **IEEE 802.15.4** (Thread / Zigbee, Matter-capable).
- Wired: **Gigabit Ethernet MAC**.
- I/O: up to **60 GPIOs**. Package: **QFN80**.
- Dev kits: **Function-CoreBoard-1** and **Korvo-1** (Espressif,
  announced with the mass-production release).
- Toolchain: ESP-IDF **v6.1** carries the S31 as a *preview*
  target (`CONFIG_IDF_TARGET_ESP32S31`, preview targets enabled);
  the org's IDF work targets v6 — see `docs/esp-idf-v6.1-bringup.md`.

Sources: Espressif ESP32-S31 mass-production announcement
(2026-07-27), Hackster on the Function-CoreBoard-1 / Korvo-1
kits, `docs/esp-idf-v6.1-bringup.md` in this repo.

## Flash map — STUB (waiting on vendor geometry)

Not yet writable. Espressif's announcement does not state the
S31's flash size or map, and this profile does not guess either.
When the datasheet (or a kit schematic with the flash part
populated) lands, this section gets the same proposed eFirmware
layout table as the M55M1 profile: secure loader, Slot A, Slot B,
update state, as flash offsets.

Known constraints the layout must respect when it is written:

- The image format is `efw_image` A/B (the eBoot-verified scheme
  every eFirmware profile uses); the slot sizes follow from the
  real flash size, not from this document.
- ESP-IDF's own partition scheme for the preview target is the
  starting point for the proposal — the eFirmware layout is
  written against it, not over it.

## Boot flow (proposed, pending the flash map)

1. S31 ROM bootloader (vendor) loads the eBoot stage from the
   secure-loader region once the flash map exists.
2. eBoot parses the slot-active flag from update state, then
   `efw_image_parse()` + `efw_image_verify()` the active slot
   (156-byte header, SHA-256 payload digest — the same
   byte-compatible scheme as the M55M1 profile).
3. Verified slot → jump to its entry. Failed slot → try the other
   slot (rollback). Both fail → recovery over the kit's USB/UART
   channel.
4. Trial-boot: a freshly updated slot must confirm boot before
   the slot-active flag commits, or the loader falls back to the
   known-good slot — identical semantics to the other profiles.

## Security partitioning — STUB (waiting on vendor data)

Not yet writable. The S31's security capabilities (secure boot
flow, flash encryption, any isolation hardware) are not stated
in the announcement material this profile is sourced from, and
the SRAM split proposal depends on the application profile, not
the announcement. This section is written from the datasheet's
security chapter when it lands. One carry-over from the org's
ESP-IDF v6.1 notes: `CONFIG_SPIRAM_ENC_EXEMPT` carve-outs, if
this design ever uses them, must never hold keys or PII-adjacent
buffers (see `docs/esp-idf-v6.1-bringup.md`).

## `efw_image` slot layout — STUB (follows the flash map)

Slot offsets and payload budgets are arithmetic on the flash
size; with the size unpublished there is nothing honest to write
here yet. The format facts that do not depend on geometry:
pack with `efwtool`, set `EFW_IMG_FLAG_SIGNED` +
`EFW_IMG_FLAG_HASH_SHA256` for production images, and treat
SHA-256 as integrity only — authenticity needs
`efw_image_attach_signature()` plus caller key validation before
a slot is marked bootable (same rule as the M55M1 profile).

## Board-specific handling

- **Dual-core cache erratum (ESP-IDF v6.1.0, Espressif #18948):**
  on S31 dual-core bring-up, the parked core leaves branch
  prediction enabled while the running core accesses flash,
  producing a layout-sensitive "Cache access error"
  (MCAUSE 0x19). Any eFirmware S31 bring-up on v6.1.0 carries
  the workaround — disable branch prediction on the parked
  core — until Espressif ships the fix. Full note in
  `docs/esp-idf-v6.1-bringup.md`; eos records the same errata
  in its `boards/generic-esp32s31.yaml`.
- **Preview-target status:** v6.1 support is preview-grade.
  Pin the IDF version in any bring-up report; do not treat a
  v6.1.0 S31 result as stable-platform evidence.
- **LP core:** the 40 MHz LP core + 32 KB LP SRAM is the
  always-on sensing path (the org's eNI/eSec low-power tracks
  care); no eFirmware handling is defined yet — that is design
  work, not a stub of missing vendor data.
